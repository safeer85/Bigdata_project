\chapter*{Abstract}
\addcontentsline{toc}{chapter}{Abstract}

A ride-hailing operator needs two answers that do not fit the same
processing model. A dispatcher needs to know which vehicles are idle and
which zones are earning \emph{now}, within seconds, and does not mind if
one trip is missing. Finance needs to know which vehicles are becoming
unprofitable once fuel and maintenance costs are applied, and that figure
must be exact, complete, and restatable when a fuel partner resubmits a
corrected file days later. This report presents a data platform that
answers both from one immutable master dataset, and defends the
architecture that makes doing so possible.

We implement a \textbf{Lambda architecture} and reject Kappa explicitly.
The decisive argument is not latency but \emph{recomputation cost}: the
correction that forces a restatement does not arrive in the event stream
at all. It arrives on a separate channel, as a daily CSV drop, long after
the telemetry it relates to, so replaying the log --- Kappa's entire
recomputation story --- does not address the actual source of
restatement. A date-partitioned Parquet lake lets the batch layer read
exactly the one partition it needs, reconciling a full simulated day in
9.4 seconds, where Kappa would require Kafka retention measured in months
to offer the same guarantee.

Lambda's best-known weakness is two codebases that drift. Our mitigation
is structural: a shared \code{common/} package holds the simulated clock,
zone mapping, validation, haversine distance, fare maths and all seven
profitability flags, and is imported by the simulators, the speed layer,
the batch layer and the serving API. Two duplications exist deliberately,
both to avoid a per-row Python UDF, and each is pinned to its Python
counterpart by a test that feeds identical inputs through both
implementations.

The system ingests a Kafka telemetry stream from a 50-vehicle simulated
fleet and a daily expense file from fuel and garage partners, on a
compressed clock where one real second is one simulated minute. Spark
Structured Streaming archives the raw stream and computes live views;
Airflow orchestrates a nine-task PySpark reconciliation per simulated
day; PostgreSQL serves both layers side by side behind a FastAPI surface
that labels every figure \code{source: speed} or \code{source: batch} and
never blends them.

The central evidence is quantitative and, deliberately, unflattering. The
speed layer runs a 10-simulated-minute watermark against injected
lateness of up to 20 minutes, so the two layers are \emph{designed} to
disagree. Over four reconciled days the revenue drift was
0.000000, 0.003384, 0.000000 and 0.000000. The one non-zero day is
attributable to a single late \code{trip\_end} event dropped by the
watermark and recovered by the batch layer
(\code{speed\_trips} 316 against \code{batch\_trips} 317). We then
measured \emph{why} the drift is usually zero --- 15 rows dropped per day,
of which 3.4\% are revenue-bearing, giving an expectation of about half
an event per day --- and report that arithmetic rather than inflating the
fault rates to manufacture a larger number. Recomputation is demonstrated
directly: a corrected \code{v2} expense file reproduced the same 50 rows
with different values, and a forced replay returned bit-identical
figures.

Observability spans all five pipeline stages: structured JSON logs
carrying both wall-clock and simulated time, Prometheus metrics for
arrival, progress and correctness, and ten alert rules of which five have
been verified firing \emph{and delivered} end to end, with a sixth
deliberately suppressed by an inhibition rule. 202 automated tests pass,
and a 28-check smoke test passes against the live stack from a fresh
clone.

Six defects found by operating the system --- not by reading the code ---
are reported in full, including a green healthcheck on an archiver that
had silently stopped writing for 26 minutes, and an interval expressed in
real seconds that was 60 times longer than intended in business terms.

\chapter*{Acknowledgements}

We thank the staff of the Department of Electrical and Information
Engineering, University of Ruhuna, for the module and the environment in
which a project of this scope could be attempted inside two weeks, and
the lecturer in charge of EC8203 for a brief that was specific enough to
argue with --- the tension between its two sub-questions is what made the
architecture decision worth making rather than merely worth stating.

This system is assembled almost entirely from open-source work. We thank
the maintainers of Apache Kafka, Apache Spark, Apache Airflow,
PostgreSQL, FastAPI, Prometheus, Alertmanager, Grafana and Docker. We
also thank the authors whose published arguments about Lambda and Kappa
we engage with in Chapter~\ref{ch:literature}; disagreeing with a
well-made case is a far better way to learn an architecture than
accepting one.
